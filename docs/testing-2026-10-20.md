# v0.3.0 validation — 20 October 2026

This is an implementation and boundary-validation record, not a REA cracking-resistance score. The supplied article is a motivating scenario; its reported timings were not independently reproduced.

## Implementation changes

| Failure addressed | Implemented behavior |
|---|---|
| Reversible stored reference passwords | Fixed-profile Argon2id PHC records with random salts; reject malformed or resource-inflating records before KDF construction |
| Keys distributed with encrypted assets | AES-256-GCM assets use an externally held 256-bit master key, per-package HKDF-SHA256 derivation, random salt/nonce, and trusted product/release/purpose/asset identity |
| Old source, debug files or answer samples shipped accidentally | Optional exact release file allowlist, forbidden path components and old SHA-256 digests, plus aggregate-budget literal scanning across the selected release root |

The new crypto interfaces are Python APIs and CLI commands. No native C/C++ verifier/decryptor SDK, server authorization service, code virtualizer or generic EXE/DLL encryptor was added. PE/ELF metadata checks still apply to the selected artifact, not every binary in the release root.

## Local test evidence

- Linux x86-64, Python **3.12.14**, `cryptography` **50.0.2**, GCC/G++ **13.3.0**, CMake/CTest **4.4.4**.
- **259 tests passed, no skips, 13.694 seconds**, exit code 0.
- The initial environment lacked CMake: the baseline ran 173 tests and skipped the CMake integration class. CMake was installed from its official PyPI distribution before final validation; that earlier skip is not included as a successful integration test.
- Final tests include real Release CMake builds, automatic C++17/seed-header integration, a pure-C shared library with a public caller, expected gate failure followed by recovery, C++ masking across optimization settings, crypto/CLI tests, and the existing signing, PE/ELF and inventory regressions.
- New boundary tests cover hostile PHC parameters, wrong passwords, asset tampering, wrong keys, all four context substitutions, canonical encoding, payload size limits, exclusive output creation, key-file identity changes, Windows stat/fstat timestamp semantics, release allowlists, known-old hashes, multi-encoding sidecar literals, scan budgets and FIFO replacement.

Reproduce with this checkout and a working CMake/CTest/GCC toolchain:

```bash
PYTHONPATH="$PWD/src" python -m unittest discover -s tests -v
```

If CMake is outside PATH, set `RELEASEGUARD_CMAKE` to its real executable. The final recorded run used an absolute `PYTHONPATH` so the CMake subprocesses also found the checkout.

## Functional cryptographic controls

```bash
PYTHONPATH="$PWD/src" python benchmarks/crypto_boundary.py --out crypto-boundary.json
```

The [recorded output](results/crypto-boundary-2026-10-20.json) uses fresh synthetic values without exporting passwords, master keys or plaintext. Observed:

- The reversible-reference control recovered its answer, as expected.
- Argon2id accepted the correct candidate and rejected the wrong candidate. The random password was absent from its serialized verifier; substring absence alone is not a cryptographic security claim.
- A deliberately weak three-entry password dictionary recovered the correct password despite Argon2id. This is an intentional negative control.
- Asset round-trip matched; wrong key, ciphertext modification and wrong product/release/purpose/asset identity were rejected.
- Authorized plaintext was available in process memory after decryption. Memory-dump resistance is **not provided**.

One Argon2id creation took 71.464 ms in this run. This is one local observation, not a latency distribution, memory-usage measurement, benchmark against REA, or estimate of guessing difficulty for an arbitrary password.

## Independent review and remaining work

A separate agent reviewed the crypto, CLI and gate changes and independently ran the 62 password/asset/CLI tests. Review found no new authentication bypass or secret-value output; it is not a third-party security audit. The review also identified Windows cross-API timestamp and FIFO-read concerns, which were fixed before the final complete suite.

The official REA source reviewed was commit `f93a0335a8c1a60bbf6debdca16675ba303e4422` (source package version 6.7.0), including Frida runtime instrumentation. Source review is not a completed REA/provider/model experiment, and does not establish npm publication status. This revision has **no new end-to-end REA success-rate measurement**. The earlier REA 6.5.0 environmental failure remains historical evidence, not proof of protection.

The [GitHub CI workflow](../.github/workflows/ci.yml) runs Linux/Python 3.10 and 3.13 and Windows/Python 3.12, native builds and the new functional crypto controls. This report records local results; consult [the Actions runs for the exact commit](https://github.com/Afloat16/anti-rea-forge/actions) for remote status. Windows DLL ABI and Windows reverse-engineering resistance remain unvalidated.

Trusted directories, key custody, rate/concurrency limits, signed-manifest public-key pinning, and trusted installation/loading remain necessary. Gate checks are not an atomic snapshot against hostile filesystem mutation; AEAD does not prevent a key holder from forging assets; neither Argon2id nor encryption prevents a client patch or functional reimplementation. See the [integration guide](crypto-protection.md) and [security policy](../SECURITY.md).
