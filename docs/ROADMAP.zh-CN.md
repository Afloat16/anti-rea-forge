# Anti-REA Forge 公开挑战与路线图

我们希望与社区一起提高保护自有软件的工程质量，并测量防护措施是否增加了指定逆向任务的成本。以下未勾选项目都是待完成工作，没有承诺发布日期或破解概率。

- [x] 外部 256 位密钥、HKDF-SHA256 与 AES-256-GCM 数据资产封装。
- [x] 最终发布文件清单、源码/备份路径、旧制品哈希与有界全目录文字检查。

- [x] Windows/MSVC EXE 构建、运行和发布检查 CI。

完整现状见 [测试报告](testing-2026-10-15.zh-CN.md)。当前没有已验证的“高概率防 REA”方案。

## 挑战 1：把 REA 测试跑完整

需要愿意搭建正常 REA/Ghidra 环境的贡献者。在自有样本上固定包版本、provider、模型（如使用）、配置和预算，保留原始输出，并验证分析结果是否能完成指定任务。

**验收：** 提供可复现命令、样本 SHA-256、环境、成功/失败/超时/环境故障分类，以及实际功能验证。只跑帮助命令、字符串搜索没有命中或 provider 启动失败，都不算防护成功。可以先提交最小环境诊断改进，无需一次完成整套实验。

## 挑战 2：补齐 Windows EXE/DLL

需要 Windows、MSVC 与原生库使用经验。构建仓库自有 EXE 和 DLL，验证保护前后输出，以及原调用方的加载、导出和调用约定。确认发布门禁在错误策略下能阻止构建，恢复策略后可重新构建。

**验收：** 记录编译器、架构、CMake、构建选项、日志、文件哈希和调用方结果。CI 工作流存在不等于这项已经通过。

## 挑战 3：拿出可测量的防护改进

欢迎提出编译期变换、关键逻辑划分、签名验证接入或其他可审阅方案。先解释要保护的资产、攻击者能力与代价，再做小范围原型。当前 `RG_TEXT` 是可逆静态掩码，不能在客户端保存永久秘密。

**验收：** 同时提交功能与兼容性对照、指定恢复任务、工具版本、固定预算、原始证据和失败样例。更换种子、删除分析工具的运行条件或检测某个探针，不能单独证明保护更有效。候选方案首先是研究提案，合入不自动意味着抵抗已验证。

## 适合第一次参与

- 改善文档命令、错误信息和新手接入步骤。
- 补充 REA/Ghidra 启动前的只读环境诊断方案。
- 添加一个自有最小样本或已有缺陷的边界测试。
- 帮助复现已公开的失败结果，并写清环境差异。

从 [贡献指南](../CONTRIBUTING.md) 开始，通过 Issue 模板提交实验或提案。只分析自己拥有或明确获授权的样本，不上传真实凭证、生产密钥或客户数据。我们欢迎成功恢复的证据，也接受诚实的未知结果。
