# Anti-REA Forge 1.2.0 — Expanded recovery controls

Release date: 2026-11-18. Python core and JavaScript SDK use **1.2.0**.

This release expands the real REA experiments from single fixtures to different
programs and builds, and closes three demonstrated disclosure paths. It keeps
the previous controls and their failures. The measurements describe what the
specified readers recover from authored release artifacts; they are not a
general probability of preventing reverse engineering.

## 1. Finish Wasm linking before release

`name` is not the only place a helper can be named. A real WABT
`--relocatable --debug-names` build retains `linking` and `reloc.Code`; removing
the debug-name section alone leaves an internal helper recoverable by REA.

The bounded envelope reader now records `linker_sections` and
`evidence.linker_metadata_present`. Default portable inspection reports
`native_metadata_unverifiable` with reason
`linker_metadata_requires_final_link` and an incomplete metadata flag.
`split-wasm-debug` rejects before creating either output. The rule recognizes
the section names; it does not pretend to parse linker symbol/relocation tables
or delete data that a linker might require. Some such modules are executable.

The five ordinary modules still separate successfully. Each private original is
byte-exact, all retained public sections keep their bytes and order, and the
public notice custom section survives. Runtime users of removed debug custom
sections can observe the change; test the actual embedding.

## 2. Treat readable source as a disclosure even in an incomplete map

The escaped JSON key `sourcesCont\u0065nt` decodes to `sourcesContent`. Source
text is still readable when `mappings` is missing, numeric or otherwise not a
valid mapping string. The old structural recognizer required a valid-looking
map and could miss this disclosure while the literal key was already blocked.

The bounded JSON traversal now applies the same conservative key rule after
decoding. It produces `source_map_marker` with
`representation: "json-decoded-key"` when existing literal/structural findings
have not already rejected the document. It works within the existing encoding,
XSSI, archive, node and depth bounds. It is a disclosure marker, not a claim
that the document is a valid v3 source map.

The expanded corpus includes three-source builds, two linked bundles, Unicode
sources/keys and a `null` original. The unavailable original is excluded from
recovery counts. A nested indexed map exposes two originals but remains outside
the flat-map splitter profile and is explicitly rejected. A partial REA graph
can demonstrate positive recovery; it cannot establish absence.

## 3. Inspect the representations real key consumers accept

The new key control executes Node key imports and byte-array decoding, plus
cryptography signing and authenticated decryption. The 19 inputs are specific
representations, **not 19 independent vulnerability classes**. They cover:

- JWK Base64 alphabet, folding, ignored characters, padding, unused bits and
  Node's UTF-16 consumer aliases, including non-BMP and surrogate inputs.
- Leading-zero RSA integer representations that preserve the actual key.
- Configured asset keys in integer-valued JSON numbers, contiguous windows in
  longer byte arrays, folded Base64 and mixed-case hex.
- Whole JSON strings containing supported unencrypted private DER in hex or
  Base64, including ignored separators accepted by the decoding consumer.

Consumer recognition is distinct from canonical JWK validation. Supported JWK
families with nonempty declared private fields that cannot be completely
inspected now produce an explicit incomplete-inspection finding. They are not
counted as positively identified keys. Normal public keys remain allowed.

A separate 38,744-character ignored-byte representation still decodes to the
configured 32-byte key in Node. The known-key reader now checks a bounded raw
prefix: enough significant characters exclude an exact 32-byte whole-string
key, while an undecidable over-budget prefix explicitly blocks release. A
complete key followed by padding and a long ignored tail is still detected.
This regression is recorded as one budget rejection, outside the 19 positive
identifications.

JSON keeps its 8 MiB file, node and depth limits. Raw JWK fields are bounded
before allocating consumer normalization; whole-string known-key Base64 has a
32,768-character raw prefix budget. Encoded DER has a raw text inspection
bound, a 64 KiB per-candidate decoded limit, at most 64 candidates and a shared
256 KiB decoded-candidate budget per JSON document. Only private ASN.1 candidates
reach the cryptographic reader. Unsupported or over-budget recognized material
must not silently become a complete, successful scan. No secret values or JSON
property names are copied into findings.

## Upgrade notes

The CLI/import names, SDK methods and signed-document v1 formats are unchanged.
Default release decisions become stricter in these cases:

1. Finish final linking for Wasm files containing `linking` or `reloc.*`, then
   separate debug information and test the application. Renamed files and
   inspected ZIP/ASAR members receive the same metadata decision.
2. Remove private source content even from malformed or nonstandard JSON maps.
   Merely naming the reserved content key may trigger the conservative rule.
3. Keep private key material and known external asset keys outside releases in
   every accepted consumer representation. Resolve incomplete inspection; do not
   treat it as a successfully checked public key.
4. Install matching 1.2.0 core/SDK archives and regenerate exported build assets
   when upgrading. Sign and package only after all applicable checks succeed.

## Required validation and downloadable evidence

The final local candidate ran 913 Python tests: **900 passed, 13 skipped, zero
failures**. All 65 SDK tests and 10 real CLI integration tests passed, as did
fresh wheel, source and SDK installations. Local tool-dependent skips are
explicit; these results do not replace required CI. The [local record](../results/validation-v1.2.0-local.json)
binds tested source hashes and identifies its uncommitted candidate state.

The required recovery CI job now runs both expanded corpora against npm/source,
the v1.1 key-representation control, and the existing v1.0 key, single-fixture
REA and Craft controls. Portable tests run on all three operating systems.
Every fresh wheel and source installation must also reject a consumer-compatible
key array, an escaped incomplete map and relocatable Wasm. The publisher requires
all three new installation booleans to be true.

Publication still requires **all 13 named CI jobs** at the exact main commit,
clean installed-artifact evidence, matching versions and verified uploaded
archive bytes. A skipped, missing, duplicate or unsuccessful required job blocks
publication. The release attaches `installation-report.json`,
`release-evidence.json` and `SHA256SUMS` alongside wheel, source and SDK archives.
