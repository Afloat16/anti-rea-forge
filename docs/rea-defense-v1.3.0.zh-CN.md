# v1.3：继续关闭可复现的泄漏入口

日期：2026-11-18。对照基线为已经公开发布的 **v1.2.0**，本轮版本为 **v1.3.0**。

本轮继续从旧版仍能放行、真实工具仍能恢复的发布物入手。修复覆盖 Python 整数密钥、
原生程序内嵌 LLVM IR、JSON 外层编码的 PEM 私钥，并新增“当前私有文件引用”来降低服务
源码和配置误发到客户端的风险。每类结论都保留实际恢复、修复后决策和正常行为对照。

这些结果证明指定泄漏路径受到阻止，不证明所有客户端代码都无法逆向。公开的 Python、
JavaScript、原生指令、运行时数据和合法服务输出仍可分析。真正需要保密的实现应保留在
独立可信端；本轮提供可直接接入已有能力凭证验证的服务示例与构建检查。

## 1. 两种真实 REA 分发

| 分发 | 固定身份 | 本轮使用 |
| --- | --- | --- |
| npm | REA 6.9.0，仓库 lockfile 固定安装 | 读取 Python PYC 的完整常量证据；分析 JavaScript 应用布局 |
| 源码 | `morluto/rea@675287517c98c702ee88ad036c5e3b8dd4bcc7a7` | 独立构建后重复相同对照 |

驱动验证工具身份、完整度和输入摘要。源码版记录干净源码树、构建工具与编译输出清单，
实验结束再次核对。两种分发的证据封装差异按实际格式处理；解析错误不会计成“防护成功”。
这些是实际 CLI provider 调用，没有宣称执行完整自主代理或模型推理任务。

新实验均将官方 v1.2 wheel 的 SHA-256 与安装后的每个包文件绑定。基线摘要为：


基线与候选包在实验前后都核验完整文件清单。复现命令、资源上限和升级步骤见

## 2. Python 字节码整数密钥

问题不是文件内直接出现原始密钥。自有程序将 32 字节资产密钥保存成大整数，再用
`int.to_bytes(32, byteorder, signed=...)` 恢复。PYC 中没有完整原始密钥或其十六进制
字符串，v1.2 检查通过；REA 的实际 PYC provider 仍可返回该整数常量，随后按标准整数
转换即可得到有效密钥。

| 项目 | 测量 |
| --- | --- |
| 表示样本 | 12 种：marshal 2/4、大小端、有符号/无符号，以及前后零字节 |
| 实际恢复 | 两种 REA 分发各 **12/12**，每次使用恢复出的密钥完成 AES-GCM 认证解密 |
| 旧门禁 | 12 种均允许 |
| 新门禁 | 独立 PYC 与真正可执行 ZIP 应用中均 **12/12 正面检出并拒绝** |
| 功能对照 | 普通 PYC 与 ZIP 应用仍执行四组公开计算，输出保持一致 |
| 未配置密钥 | 工具仍能恢复，该规则允许；明确保留为边界 |
| 短有符号整数 | 工具仍能恢复，检查明确记为不完整并拒绝；不计入 12 个正面检出 |

新检查只生成已配置密钥的规范 marshal 整数模式，不解析执行不可信 Python，不调用
`marshal.load`。范围是稳定 CPython 3.7–3.14 的头部与规范整数表示；它既不证明整个
marshal 对象有效，也不处理任意计算、拆分或非规范表示。检查器本身仍要求 Python 3.10+。
详见 [PYC 检查范围与官方源码依据](python-pyc-key-profile.md)，以及
[npm](results/python-key-recovery-v1.3.0-rea-6.9.0.json) /
[源码版](results/python-key-recovery-v1.3.0-rea-source.json) 原始统计。

## 3. strip 后残留的 LLVM 编译器 IR

真实 Clang `-fembed-bitcode=all` 产物经旧分离器处理后，普通符号虽已移除，`.llvmbc`
和 `.llvmcmd` 仍被发布。`llvm-dis` 能读出 **4 个私有名称、源码路径和算术实现**。
这比从机器码重建逻辑提供了更直接的原始编译信息。

v1.3 将编译元数据与调试元数据分开报告，并把符合条件的 ELF 编译段完整留在私有文件。
分离前检查段类型、标志、链接语义及与所有文件承载程序段的重叠，分离后核对私有段
大小和哈希、原生 `.text`、动态符号及运行段。原始、v1.2 公开件和 v1.3 公开件的三组
运行退出码均为 **48、85、122**。重新放回 `.llvmbc` 后，恢复入口重现且发布门禁再次拒绝。

“公开侧没有嵌入 IR 可供读取”只描述该发布通道。分离器没有改变公开机器码，也不能阻止
反汇编器分析它。PE 与 Mach-O 的规范 LLVM 段也进入元数据审计；本轮新增这两种格式的
验证是结构解析测试，没有声称新执行了对应平台的编译产物运行实验。

另外，真实 Clang 产生的原始 bitcode 与 Apple 目标包装 bitcode，在改名与双层 ZIP
四种布局中都被旧版放行。新版识别签名后记为 `unsupported_standalone_metadata`，
原生检查完成状态为 false。它们是未支持输入的保守拒绝，不是“四次成功解析”或
“分析器恢复失败”。包装样本只验证 IR 生成和读取，没有执行 macOS 原生程序。

[Clang / llvm-dis 配对数据](results/llvm-metadata-recovery-v1.3.0.json) 来自 Linux
Clang 19.1.7；必需 CI 用 LLVM 18 独立运行同一控制。

## 4. 当前私有文件引用与服务布局

旧 `forbid_file_sha256` 可以拒绝已知完整副本，但私有源码变化后，手填的旧摘要会失效。
`private_input_files` 将声明的私有文件作为可信构建输入：每次检查重新读取当前内容，
在磁盘、受检 ZIP/ASAR 和已核验的解包旁文件中匹配完整副本。`prepare` 在扫描、签名、
写入和最终验证期间复核，输入变化即失败，已创建的新证据目录按既有回滚流程清理。

真实 REA 应用图的三侧对照如下：

| 布局 | 私有源码节点 | 分析完整 | 配置后的门禁 |
| --- | ---: | --- | --- |
| 误发私有文件 | 1 | 是 | 拒绝 |
| 只发布客户端 | 0 | 是 | 允许，`prepare` 成功 |
| 放回相同私有文件 | 1 | 是 | 拒绝 |

两种 REA 分发结果一致。另一个变化对照先更新私有源码：旧手填摘要允许新副本，当前
文件引用则拒绝。见 [npm](results/private-input-controls-v1.3.0-rea-6.9.0.json) /
[源码版](results/private-input-controls-v1.3.0-rea-source.json)。0 表示没有向该客户端
交付这份精确源码，不表示算法行为无法从输入输出推断。

每次最多 64 个明确文件，单个 1 字节至 8 MiB，总计 64 MiB，必须在公开根目录外；链接、
重解析点、目录、特殊文件、缺失和变化均失败。API 不会递归导入或执行源码。输出不新增
外部私有路径或独立参考摘要，但公开清单仍包含被发布文件本身的摘要。

**这是完整文件匹配。** 追加、编译、混合、拆分和编码都会改变指纹，不能靠它证明这些
变体没有泄漏。构建依赖图、输出白名单和私有端部署仍需要明确设计。
[私有服务示例](../examples/private_service) 复用已有固定 issuer、认证身份、能力范围、
过期与持久重放检查；未引入新网络协议，也没有把它包装成新发现的授权漏洞修复。

## 5. PEM 私钥外层编码

JSON 中的 PEM 私钥如果再经 Base64/十六进制编码，v1.2 默认检查允许，但 Python/Node
标准消费者可以恢复并实际签名。v1.3 增加一层外包装的有界检查，包含消费者接受的前导
说明、折行、忽略字符和 UTF-16 低字节别名。

| 类别 | 数量 | 实际结果 |
| --- | ---: | --- |
| 可恢复表示 | 8 | 8 个签名均验证成功；新版正面识别 8 个，旧版全部允许 |
| 非秘密对照 | 2 | 公钥 PEM 与较大普通数据均允许 |
| 超预算但仍可恢复 | 2 | 解码/签名有效；新版明确不完整并拒绝，排除在 8 个检出之外 |

PEM 与 DER 共用每 JSON 文档 64 个候选、256 KiB 解码字节预算；每候选限制 256 KiB
原始字符串和 64 KiB 解码数据。交叉审阅发现了“假编码提示已发生解码却不计数”的问题，
本轮一并修复并加入回归。现在每次实际候选解码都记账，最终无真实 PEM 标记时仍可作为
普通字符串通过，重复超量则明确拒绝。[完整消费者实测](results/encoded-pem-recovery-v1.3.0.json)

此处的 PEM 头部判定与已有原文标记一致，是保守泄漏证据，不保证每个带标签的文件都
是数学有效私钥。嵌套多层编码、拆分与任意计算不在该检查范围内。
