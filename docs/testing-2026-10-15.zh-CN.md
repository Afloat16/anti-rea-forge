**功能正常，但当前防反编译与防破解目标未达到。** 完整测试口令虽然没有以明文出现在受保护样本文件中，仍被独立 Ghidra 静态分析和独立运行时观察分别恢复；未修改的原程序接受恢复值。这些结果不能支持“高概率防 REA”或“开源后别人也无法破解”的表述。

## 环境与复现

Linux x86_64，Python 3.12.14，cryptography 50.0.2，GCC/G++ 13.3.0，GNU binutils 2.42，CMake/CTest 3.31.6，npm `rea-agents@6.5.0`，Ghidra 12.1.4，Eclipse Temurin JDK 21.0.12.1+1。依赖装在测试工作目录中，没有修改 REA、Ghidra 或系统进程检查。

从已安装项目的虚拟环境运行；若 CMake 不在 PATH，请先设置 `RELEASEGUARD_CMAKE`：

```bash
python -m unittest discover -s tests
python benchmarks/native_compare.py --out comparison.json
python benchmarks/runtime_boundary.py --out runtime-boundary.json
```

最后一条命令仅生成、执行和清理自己的 Linux/GCC 临时样本，不接受用户提供的二进制。它明确使用 `-fno-builtin-strcmp` 固定动态比较边界；这不覆盖内联比较、其他工具链或复杂业务。探针保留真实比较结果，只对新建样本子进程设置 `LD_PRELOAD`。随后清除 `LD_PRELOAD`/`LD_AUDIT`，验证恢复值被接受、`WRONG` 被拒绝，并比较文件 SHA-256。报告只保存测试口令摘要，退出 0 表示实验完成且恢复成功；依赖缺失或没有捕获时返回 2，保护结果为 `unknown`，不能计为防护通过。

初始二进制盲测与该自动复现实验分开进行。后者为公开的边界演示，分析方法已知，不再属于盲测；不能将两个观察当作独立业务样本计算成功率。首轮自动实验耗时约 0.589 秒，包含小型样本及探针编译，不代表真实业务攻击时间。

盲测输入范围由本轮协作流程记录，归档补充了探针源码和捕获输出。其原始验证 JSON 没有记录前后文件哈希，不能单独充当完整盲测审计链；关联样本哈希是在归档时补记。静态恢复验证和自动运行时复现实验分别保留了文件前后哈希，结论不依赖补记记录。

## 独立 Ghidra 静态恢复

样本 SHA-256：`e745495228de8b2ad64de3f5189505cdc2bc9ea007318010682127302645717b`。它使用 GCC C++17、O2、LTO、strip 和 v0.2.0 文字组件，构建种子 `0123456789abcdef`。样本源代码、二进制及答案在分析结束后归档，答案仅是本轮随机合成测试数据，没有发行私钥或客户凭证。

分析方在读取 fixture 源码和答案前，根据 Ghidra 输出的解码器循环及常量完成静态恢复。主要入口为 `0x001010a0`，解码器 `0x00101220`，比较调用方 `0x001012c0`。ELF 的 `0x2030` 文件偏移提供前 40 字节，剩余一个栈常量来自比较调用方伪代码。恢复出的 41 字节包含末尾 NUL。随后与保留答案核对一致，再将恢复值交给未修改的原程序，返回 `ACCEPTED` / 0，前后文件哈希相同。

分析及导出耗时 26.989 秒；24 个反编译响应包含 8 个外部入口占位，不能称为恢复 24 个有效函数体。比较返回值的反编译建模存在误差；本结论只需要解码算法、常量与实际接受验证，不声称完整源代码或全部行为已恢复。

归档 [证据目录](results/testing-2026-10-15/) 包含伪代码、脚本、样本和 JSON。仅对这个归档样本可复放已经观察到的恢复：

```bash
python docs/results/testing-2026-10-15/ghidra/recover_sample_literal.py \
  docs/results/testing-2026-10-15/fixture/sample.elf
```

脚本中的地址和常量固定于此样本，不能当成通用提取器。它只读取样本字节；真正的分析输出同时保留。Ghidra 的 Java 导出脚本为同目录下的 `ghidra/ExportPseudocode.java`，可在正常安装环境通过官方 `analyzeHeadless` 的 `-scriptPath`、`-postScript` 使用。本机因缺少 `/dev/fd` 无法运行标准 shell 启动器，改用官方 LaunchSupport 输出的 VM 参数和同一个官方 Java headless 入口；完整命令记录在 `sample-direct-headless-summary.json`。GNU demangler 执行遭权限拒绝，未改安装包；这没有阻止本次解码器分析。

## REA 整合测试的环境阻塞

实际调用了 npm 包的 CLI，而不只是阅读源码。例如：

```bash
node /path/to/rea-agents/scripts/rea.mjs inspect-with-objdump /path/to/sample disassemble --json
node /path/to/rea-agents/scripts/rea.mjs inspect /path/to/sample --provider ghidra --json
```

objdump 相关操作 3 项返回 `capability_unavailable`；诊断显示 REA 的子进程归属检查需要可用的 `ps` 和 `/proc`，本机 `ps` 返回 47。Ghidra 整合调用在配置进程局部 Java 库路径后，仍因固定 `/tmp/rea-ghidra-*` 父目录不存在而失败；普通 `TMPDIR` 设置无法改变这一路径。本轮没有伪造 `ps`、挂载 `/proc` 或更改 REA 安全检查。

独立 Ghidra 已成功分析同一保护样本，但它不等于完成了 REA 的 provider 与 agent 流程。故障记录保留在证据目录，REA 整合项记为环境阻塞，不计入防护成功或失败比例。

## 结论的范围

- 该掩码能减少直接明文搜索入口，但不能保住解码器和运行时需要的永久口令。门禁通过与保密成功是两项不同性质的结果。
- 本轮没有伪造 Ed25519 许可证、恢复发行私钥或验证完整授权系统的安全性；合成口令样本不等同于真实签名授权方案。
- Windows/MSVC、真实 EXE/DLL、完整业务软件、IDA/Hopper/Frida 及配对多样本成本实验尚未执行，不能给出可信的“高概率”结论。
- 未通过检测某个探针或破坏分析器来改变实验结果。对必须保密的凭证和关键算法，应将其保留在受控服务端，并继续把签发私钥留在客户端之外。

本轮未修复出一个可宣称抗破解的新版本；保留失败结果和可复现证据。完整功能范围另见 [验证记录](validation.zh-CN.md)。
